# Customer Portal — 48-Hour Real-Usage Audit + Coding Issue Sweep (2026-08-21)

Bryan asked for two things: an audit of the last 48 hours of actual customer/staff activity (using real data, not tests) to see what's working vs. broken, and a broader codebase pass to find and fix remaining coding issues. Full technical detail is in `Customer-Portal-Process-Flow.md` (PLAN-24) on Bryan's device; the polished writeup is `Customer-Portal-48-Hour-Audit-2026-08-21.docx`, delivered to Bryan directly. This doc is the project-side pointer.

## Method

Pulled real Vercel production error/log data for the project (48h window) and the real Monday.com update history across every order for the same window — actual customer and staff activity, not synthetic tests.

## Working correctly

Every full order-completion flow traced in the window (Natalie Whicker/HASC MT, Kristel Kirk/Pitt LLC, Stepping Stone) landed with fully correct data. Reminders correctly scoped to genuinely-incomplete steps for every order checked, confirming PLAN-12's fix (4) holds under real load. Staff's "View as Customer" assisted-entry mode is in active regular use.

## Not working correctly — found and fixed

1. **Messages badge miscounted the whole audit trail** (Rachel/Remedy Speech Therapy) — already fixed same day as PLAN-22.
2. **AfterShip 429s** — Vercel confirmed this wasn't a one-off: 1,217 occurrences over the full 48h window, continuously since the exact hour PLAN-19's concurrency change shipped on 8/19. Confirms the causal link with real timestamps. Fixed as PLAN-23 (retry-with-backoff + lower concurrency).
3. **One legacy message still shows the wrong sender** — confirmed unfixable (predates origin-tagging, no record of true sender exists).

## Same-class-of-gap sweep — 2 new proactive fixes

Having confirmed AfterShip's root cause (concurrent calls, no rate-limit handling), checked whether the same pattern exists elsewhere before it causes a real incident. It did, twice, both in `lib/monday.js`:

- Monday's own API had no handling for its rate/complexity-budget limit, despite several call sites now running concurrent Monday calls. Added the same retry-with-backoff protection preemptively — no real incident had happened yet, but the exposure was real.
- A video-link resolver (`resolveTrackedUrl`) had fetch calls that looked timeout-protected but weren't (an `AbortController` created but never wired to a timer). Fixed to match the established pattern from PLAN-14's PORTAL-021.
