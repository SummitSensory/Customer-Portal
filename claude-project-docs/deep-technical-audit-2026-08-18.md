## Remediation, round 2 (2026-08-18, same day, user-directed: "you need to make the decision how to best resolve the outstanding issues and then create those fixes")

Bryan explicitly overrode the "requires your decision" framing from round 1 and directed me to decide and implement both remaining findings. Full detail in `Customer-Portal-Process-Flow.md`'s **PLAN-15** entry — summary here:

- **PORTAL-023 (monitoring) — resolved without requiring a new third-party account.** A real APM (Sentry/Datadog) needs an account only Bryan can create, so instead of a placeholder-credential stub, built a small internal alert path on infrastructure already live in the app: new `lib/monitoring.js` (`reportCriticalFailure(source, message, details)` — always logs first, then emails) + a new `sendInternalAlert()` in `lib/email.js` (Resend, new `ALERT_EMAIL` env var, defaults to `NOTIFY_TEAM_EMAIL`). Wired into exactly 3 call sites — deliberately narrow, to avoid alert fatigue: `markSectionCompleteSafe()`'s final failure in `lib/monday.js`, and the top-level catch blocks of both cron jobs (`pages/api/cron/reminders.js`, `pages/api/cron/accessory-tracking-sync.js`). NOT wired into routine security rejections (bad webhook secret, invalid session) — those are expected/frequent enough that alerting on every one would train everyone to ignore the alerts. If real APM is set up later, `lib/monitoring.js` is the one place to redirect from.
- **PORTAL-025 (dead Email Template Management System) — archived, not deleted.** Confirmed via repo-wide grep that nothing in `pages/**` (or anywhere else) references any of the 7 files, and confirmed no build script forces `prisma generate`. Rather than deleting genuinely substantial unfinished design work (682 lines, per PLAN-11) or leaving it live and unreachable, moved `prisma/schema.prisma`, `lib/email-templates/*.js` (5 files), and `lib/permissions.js` verbatim to `_archive/email-template-system/`, with a README there explaining what it is, why it was archived, exactly what changed in the active app, and concrete steps to resume the work later. Removed the now-unused `prisma`/`@prisma/client` dependencies from `package.json` (regenerated `pnpm-lock.yaml`); removed the dead `DATABASE_URL` placeholder from `.env.example`.

## Follow-on fixes, same day (2026-08-18) — not audit findings, but same codebase/session lineage

Two more requests came in after the audit remediation closed out. Full detail is in `Customer-Portal-Process-Flow.md`'s **PLAN-16** and **PLAN-17** entries; noted here only as a pointer so a future session knows to look there:

- **PLAN-16 — message sender identity bug (Bryan-reported via screenshot).** The Admin Messages tab was showing a customer's own message under staff member "Bryan Shepherd," and Bryan separately asked that staff messages always display as "Summit Sensory Gym," never an individual's name. Root cause: PLAN-12 (2026-08-17) had already fixed this correctly for the customer-facing portal, but the Admin Messages tab never adopted that fix — it read `creator.email`/`creator.name` directly (always wrong, since Monday's `create_update` API always attributes to the API token owner) and never stripped the internal `[PORTAL:*]` tag from the visible body. Centralized the logic into a new `lib/messageOrigin.js` so both views read the same rule.
- **PLAN-17 — multi-order navigation.** A customer with 3 separate orders needed a way to move between them without confusion. PORTAL-007 (round 1) already solved the *first* order pick at login; this adds a top-bar order switcher (only shown to customers who actually have more than one order) so they can jump to any of their orders at any time afterward, without signing out. Reuses the existing `/api/auth/select-order` session-rebind endpoint, so no other endpoint's authorization logic needed to change.
