# Customer Portal — Kalen Siddens Complaint & Portal-Wide Persistence Audit (2026-08-17)

## What happened

Kalen Siddens (order `12789699126`, "Universal Exercise Unit/Spider Cage Training", email `siddensagrepair@gmail.com`) called Bryan reporting "odd errors and not seeing certain things" while trying to complete portal tasks. Rather than guess, pulled his real Monday.com record (both the main order item and its linked Delivery & Site Details Submissions row) to ground the investigation in what actually happened to him.

Confirmed from his record: he completed Contact, Billing, and Delivery on 2026-08-13 (Monday's Portal:Contact/Billing/Delivery status columns all show ✅), submitted a Messages-tab complaint reading "Wouldn't let me change cage color," and never completed Color Selection or Required Documents. On 2026-08-17 he received an automated reminder email incorrectly claiming Contact Information was still incomplete — four days after Monday's own record showed it done.

## Six root causes found and fixed

1. **Completion status only ever read from localStorage, never from Monday's own durable status columns.** `order.progress` (Contact/Billing/Delivery/Colors/Documents) was already computed by `parseOrderItem()` but never consumed by the frontend. A different browser, cleared cookies, or staff opening the portal on another machine made a customer's already-completed steps look wiped. **Fixed:** `loadOrder()`/`OrderPicker` in `pages/portal/index.js` now merge `order.progress` in as the source of truth; localStorage is now only a same-browser cache layered on top.
2. **Color and Required Documents "Mark as Complete" buttons never called the backend at all.** Pure local/localStorage state — Monday's Portal:Color/Portal:Required columns never flipped no matter how many times a customer clicked it, even though the backend case already existed and was already used correctly by every other tab. **Fixed:** wired both buttons to `saveSetup('color'|'documents', {})`.
3. **Delivery tab's ~20 fields (secondary POC, comm preferences, loading dock, delivery timing, ship-to address components, freight-ack name) and Billing's decomposed address/contact fields never round-tripped back onto the order.** They were written only to a free-text tagged update and a separate audit board — so the form reset to blank on every remount, even right after a successful submission. **Fixed:** added two new additive Monday columns (`long_text_mm6a5z48` "Portal: Delivery Answers (JSON)", `long_text_mm6ancsh` "Portal: Billing Answers (JSON)") on the Manufacturing Process board (`6533700776`); `setup.js` now writes a full JSON snapshot on every submit (not best-effort — failures now surface as real errors), and `parseOrderItem()` parses it back as `order.deliverySnapshot`/`order.billingSnapshot`, which the forms seed their initial state from.
4. **The reminder cron (`pages/api/cron/reminders.js`) used a different, disagreeing definition of "complete" than the app itself** — text-matching one exact legacy tagged-update phrase per tab, which drifted out of sync with the real status columns (this is exactly what caused Kalen's incorrect reminder). **Fixed:** now reads `order.progress` directly, the same source of truth as fix #1.
5. **Monday's `create_update` API always attributes messages to the API token's owner, never to the actual customer** — confirmed every message Kalen sent through his own portal showed creator "Bryan Shepherd." This made a customer's own sent messages render as if they'd come from staff, and permanently stuck the unread-reply badge at 0 (whose filter polarity was separately backwards too). **Fixed:** `/api/monday/messages` now stamps true origin into the body (`[PORTAL:CUSTOMER]`/`[PORTAL:STAFF]`); the frontend reads that tag with a legacy-email fallback for pre-fix history, and the badge filter now correctly counts staff messages.
6. **Contact tab's "Submit Changes" correction flow gave a toast then reverted to showing the OLD value with no sign anything was pending** — indistinguishable from silent failure. **Fixed:** persists the pending correction locally, shows a "pending review" banner until Monday's mirror catches up, then auto-clears.

## Not fixed / flagged only

Kalen's literal "wouldn't let me change cage color" complaint (Color Selection Jotform embed) couldn't be reproduced or root-caused from code alone — plausibly the third-party Jotform iframe itself, or the `dangerouslySetInnerHTML`/React-reconciliation risk already flagged in `ColorTab`'s own code comments if he switched tabs mid-form. Worth investigating live if it recurs.
